# 用 DSPy 优化系统提示词，并揪出「多余提示反而让模型瞎猜」

- 日期：2026-07-03
- 来源：https://simonwillison.net/2026/Jul/2/llm-coding-agent/
- 主题：三、提示词与上下文管理

## 这是什么

Simon 7 月 2 日这三篇单看都像随手记，合起来却是一条很清楚的线：人退到只发提示词，Claude Fable 5 开始自己产出代码和研究。第一篇里，他只丢两句提示词，让 Claude Code 先写 spec，再用 red/green TDD 自举出一个能读写文件、执行命令、搜 repo 的编码 agent 框架，Simon 自己一行没写。第二篇是他把异步研究任务交给 Claude Code for web，让 Fable 5 去用 DSPy 优化 Datasette Agent 的只读 SQL 系统提示，还发现「已有信息就别 describe_table」这类建议会让模型瞎猜列名并反复报错重试。第三篇转 Geoffrey Litt 的提醒：开发者必须理解 agent 生成的代码，才算创作过程里的主动参与者，不然只是接收产物。前两篇展示 Fable 5 能把人推到提示词位置，后一篇正好补上刹车：你可以少写，但不能少懂。

## 可以怎么用

- 优化系统提示词时不要只顾着「加规则」，要反过来检查现有规则里有没有看似合理、实际上在误导模型的条目——这篇的例子是「已有信息就别再查工具」这类建议，反而让模型跳过验证直接瞎猜答案。可以用 DSPy 这类自动优化工具，或者手动做消融测试，逐条删规则看效果变化。
- 给 agent 写系统提示词时，多一条建议不等于多一分保险；每加一条规则前可以先问：这条会不会在某些场景下变成误导，让模型该核实的时候不核实。
- 记住 Geoffrey Litt 的提醒：即便把生成代码/研究的活全部交给 agent，也要真正理解它产出的东西，才算是创作过程的参与者，不然只是被动收货，出问题时也没有能力判断哪里错了。
