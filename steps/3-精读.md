# 步骤 3 · 派 reader + 核查 agent

## reader（金银候选，一组一个）
- general-purpose，**前台跑**，封顶 ~5 个。派活 prompt：读 `roles/reader.md` + 分到的组（文章 URL 列表）+ digest 写入路径 `reports/<date>/work/digests/group-N.md`。
- ⚠️ 派活 prompt 里**别写「帮我把对撞讲清楚 / 贯通落点在哪」**这类编排要求——reader 会返回叙事框架，污染后面的写手。要「核心主张 + 关键细节 + 档位线索」就够，编排是定牌和写手的事。
- ⚠️ **每份派活 prompt 必须写明「绝对不许派 subagent」**（2026-07-27 崩机两次的直接原因：内存不足 + subagent 嵌套派活）。另：「直读直摘」型的组（不需多源交叉核对的）主 agent 自己读更省事，别为省事而派。

## 核查 agent（无牌条目 + 乐子，1 个）
- 派活 prompt：读 `roles/核查.md`（它内部要求先读定调——label/body 它是第一作者）+ 你点名的无牌/乐子候选清单 + 输出路径 `reports/<date>/work/digests/lines.json`。
- 把 STATUS 防重复主线也带给它，它标出 dup_suspect 由你裁决。

## 验收
- 每个 reader 回一句：组主题 + 推荐强度 + 重复风险。有「旧文重炒」信号的回头调档或丢弃。
- lines.json 逐条看一眼 note：fetch_failed 的丢或换源，dup_suspect 的对照昨日 daily.json 裁决。

产出：`work/digests/group-N.md` × N + `work/digests/lines.json`。下一步 → `steps/4-写手.md`
