## 金牌是怎么来的（本期最值得记的一件事）

**这条推翻了我们 07-22 第 18 期金牌正文的一句话**：

> 事发时 OpenAI 在内部发现异常，HF 也同时拦下了活动。

那句是照 OpenAI 官方通报写的。路透版本（十余名知情人士）是：7 月 11 到 13 日入侵期间 OpenAI 没发现，7 月 16 日 HF 自己发博客后才知道是自家 agent，7 月 18 到 19 日周末翻日志才找到痕迹。两个版本不能并存。

## 写作复盘

用户本期改动量为近三期最大，自述「写手写的那版比较难懂」。逐条对照见 `用户修改.md`。当轮已落地一条规范：`roles/定调.md` 第一条加入「用大白话讲给不太懂技术的朋友听 / 专有名词可以直接丢弃 / 语言通顺内容闭环高于完整全面」。

写手自己报告的取舍是「为压字数砍掉 A 保住 B」，而用户的取舍是「为读者能懂砍掉 A，必要时给 B 更多字数」（NVIDIA 那条直接从无牌升银牌）。这两种取舍方向不同，是本期的核心教训。

## 事故与教训

1. **并行派 reader 把用户的机器搞崩了**。第一轮并行派出多个 reader，机器崩溃，只有 group-1 和 group-5 落盘。用户要求改成串行，已写进 `steps/3-精读.md` 第 4 行。后续 5 个 reader + 1 个核查 agent 全部串行跑完，无异常。
2. **主 agent 差点按命名规律猜 URL**。填工单时，金牌 URL 我照着「路透 + The Star + 日期 + 标题」的规律自己拼了一个出来，没从 digest 里读。写完后自查时发现，回查 group-7.md，真实路径的日期段和标题串**完全不同**。已改正。教训：reader 返回摘要里说「主 URL 是某某家」不等于给了 URL，凡填 URL 必须从 digest 原文读。
3. **X 源整体挂掉**。七个账号全部 HTTP 530 / error code 1033，是 `nitter.kareem.one` 这个实例的 Cloudflare 回源隧道挂了，**不是 429 限流**——昨天能通的 emollick / goodside / karpathy / NeelNanda5 今天也一样死。按规矩没当场折腾换镜像，记进 fetch_failures。**这是连挂的第二种形态（前几期是 429），下轮若仍全灭，该跟用户议换实例了。**
4. **DeepMind 博客改版**：静态 HTML 里取不到文章 href，只能读到标题和月份粒度。7 月 5 条里 3 条已报，剩 2 条（Gemini 三连、印度 ATL Saathi）拿不到精确日期和 URL，**没猜、没收**。该源下轮需要换抓法。
5. **hf-papers 没出新批次**：`/papers` 当天服务的仍是 07-24 那批（与 `/papers/date/2026-07-24` 逐条一致），07-25 页面不存在。本期三条论文都是那批里上期未收的次高票残留，非新稿。
6. **seen 回写 1 条未匹配**：金牌的 thestar.com.my 不是配置信源。判断是不用手补——`check_dup_urls.py` 的历史口径读的是往期 daily.json，这条已自动进查重库；seen.json 是给 scout 抓源用的去重表，补进去没有意义。
