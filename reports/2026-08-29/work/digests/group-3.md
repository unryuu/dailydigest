# 漏洞只露出风声，代码 Agent 就能找出利用方法

- 推荐强度: 强
- 档位线索: 有银牌线索。最硬的新意不是泛泛的“AI 会找漏洞”，而是公开补丁进入讨论约十分钟后，线上服务就出现了针对该漏洞形态的探测；同时作者实测，只给 Agent 一个大致漏洞方向，也能在一分钟内独立找到相关问题并生成本地利用。若写作时把外部真实探测与作者自己的 Agent 演示严格分开，证据足以支撑重点条目；但尚不足以证明线上探测必然由 AI 发起，也不宜写成攻击者已经成功利用。

## 核心主张

OCaml 核心维护者 Anil Madhavapeddy 修复 cohttp 的路径遍历漏洞时，公开修复 PR 约十分钟后，他的网站日志就出现了带百分号编码遍历序列的探测；这说明监控公开代码仓库的人或自动系统，已能把极少的漏洞线索迅速变成实际探测。更棘手的是，作者只告诉 Agent 大致去查路径规范化问题，DeepSeek V4 Pro 就独立找出数个相关问题，并在一分钟内生成了用于探测本地服务器的利用。作者据此认为，传统开源安全流程依赖“漏洞细节暂时保密”来争取修复窗口的假设正在失效，真正的瓶颈已转向维护者的验证、修复、发布和下游分发能力。

## 为什么值得看（钩子）

过去是补丁公开后攻击者研究漏洞，现在可能只要有人提到漏洞属于哪一类，Agent 就能自己把剩下的路走完。公开协作本来是开源修补漏洞的优势，却可能同时成为自动化探测的起跑枪。

## 关键细节 / 引述

- 漏洞最初由 Jane Street 通过私有 Slack 渠道报告，报告本身由 Claude Fable 找到；作者让 Claude Fable 检查路径规范化问题时被安全策略拒绝，随后改用 DeepSeek V4 Pro，后者独立发现了数个相关问题。
- 作者称，他的 Agent “在一分钟内”就轻易生成了探测本地在线服务器的利用；这属于作者自己的受控演示，不是线上攻击者成功利用的证据。
- 作者为了让更多人参与审查，低调公开了 `cohttp#1145`。以往这类讨论通常会持续几天，一两周内发布修复也算合理；但约十分钟后，他的网站已经收到百分号编码路径遍历序列的探测，显示有人或自动系统在监控公开仓库。
- 作者引用 Fang 等人的研究：给 GPT-4 Agent 一段 CVE 描述时，它在包含 15 个漏洞的基准上成功利用 87％；不给描述时成功率为 7％。作者的判断是，今天的 Agent 只需要一个宽泛搜索方向，就能自行完成后续研究。
- 文中称 2026 年漏洞的平均利用时间已经变成负 7 天，即利用早于补丁；作为旁证，marimo 的 CVE-2026-39987 从公告到首次利用尝试为 9 小时，Langflow 的 CVE-2026-33017 为 20 小时。这里是作者引用的行业数据，不是 cohttp 个案自身测量。
- Simon Willison 补充了 rclone 维护者 Nick Craig-Wood 的一线数据：项目前十年通过 GitHub 收到约 20 份安全披露，最近一个月却超过 40 份，其中约 75％至少有值得检查的内容；GitHub 分配 CVE 的时间也从此前约 2—3 天延长到 3—4 周。
- Anil 提出的应对不是单一“加长保密期”，而是三路并行：更私密且可信的漏洞讨论网络；公开后持续、快速发布修复；在完整补丁完成前，先下发协议层的临时缓解规则。cohttp 这次可先对请求 URL 中百分号编码的路径分隔符做规范化，类似云服务的“虚拟补丁”。
