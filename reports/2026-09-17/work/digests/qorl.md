# 用小模型给 Postgres 挑查询计划

- 推荐强度：强
- 档位线索：银条合适。结果够硬，训练过程也有方法价值；但最佳数字依赖同一数据库、每条查询三轮搜索和最多十五个候选，不宜升金。
- 涉及文章：[Training a 4B model to produce 81% faster query plans than Postgres](https://rohanbansal.com/qorl) · Rohan Bansal · 2026－09－16

## 核心主张

作者没有让模型替代 Postgres 的即时优化器，而是让它用 `pg_hint_plan` 反复试跑候选方案，专门优化会重复执行很多次的分析查询。一个四十亿参数模型先通过前沿模型轨迹学会操作工具，再用可直接测量的查询耗时做强化学习；最终在 113 条连接密集型查询上，最佳候选选择达到 1.81 倍几何平均加速，总耗时也缩短 44.7％。这套办法的交换条件很明确：前期要为每条查询多次执行和搜索，收益靠后续重复运行摊薄。

## 为什么值得看（钩子）

它把数据库优化变成了一个结果容易验证的智能体任务：模型不用证明自己“懂”成本估算，只要试出的方案确实跑得更快。更关键的是，原始小模型在 113 条测试查询中有 99 条连有效候选都给不出，训练后却能在固定数据库里找到传统优化器漏掉的计划。

## 关键细节／引述

- 测试使用 Join Order Benchmark 的 113 条查询、33 个模板；训练使用同一 IMDb 数据库上的 CEB，约 1.36 万条查询、16 个模板。作者检查过两套数据的连接图结构，没有重叠；目标本来就是让模型熟悉某一家公司的具体数据库，而不是证明跨数据库泛化。
- 未训练模型只有 14／113 条查询能产出有效候选，81 条没有有效候选，另有 16 条在最终选择时失败。经过监督微调和 1200 次强化学习更新后，单轮评测中有效候选升到 101／113，几何平均加速为 1.41 倍，总工作负载加速为 1.29 倍。
- 最终的 1.81 倍来自每条查询运行三条轨迹、最多生成十五个候选，再按实测反馈挑出最佳方案；113 条查询中有 68 条快于 Postgres 默认计划，零条回退。若采用模型自己在每条轨迹里的最终选择，339 条轨迹平均为 1.40 倍，并有 7 次回退。
- 奖励设计专门处理数据库计时噪声：候选与默认计划交错测量，对 5％以内差异不计分，并把强化学习的比较基线锚定在“不比默认计划差”，避免一组坏方案里相对没那么坏的方案也得到奖励。
- 训练先用 Astra 生成轨迹做离线蒸馏，再把推理、训练放在两张 H100 上，把四个 Postgres 测量实例留在作者本地机器。租用约 95 小时 H100 花费约 800 美元，生成教师轨迹的 API 费用约 400 美元，总成本约 1200 美元。
- 模型最常学会的三类有效动作是改写连接顺序、只修正一次扫描方式，以及启用并行执行；这说明收益不只来自背下某个完整计划，而是学到了能在搜索中反复调用的局部策略。

## 与近期的关系

近期日报没有覆盖 Postgres 查询优化或让小模型通过真实执行反馈改写数据库计划的内容，重复风险低。它与常见的“模型参数更大、基准分更高”叙事也不同，重点是一个小模型在单一、可验证、可反复试错的生产型任务上，经专门训练后超过成熟系统的默认选择。
