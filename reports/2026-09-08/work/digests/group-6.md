# Agent 究竟会不会主动使用测试与验证技术

- 推荐强度：强
- 档位线索：够银。它不是个人体感，而是同一实现任务下对 26 种提示条件和 4 个 skill 做批量对照，再逐条检查 Agent 实际做了什么；但作者明确称其为快速、尚未充分审校的实验，并省略了部分实验细节，不建议仅凭榜单升金。

## 核心主张

给编码 Agent 一句“使用 TDD／形式化验证／属性测试”等方法名，通常并不会让它真正掌握这套方法：它往往只是把原本会写的浅层单元测试塞进新框架，证明无关紧要的性质，或用大量随机无效输入反复撞拒绝路径。实验中不加额外指令的默认组反而高于平均水平，TDD 和多个现成测试 skill 都没有提高正确率，部分还显著增加成本。真正稍有希望的不是继续堆方法名，而是由人先指出高风险区域、要求能区分不同解释的非对称／边界样例，并为测试搭好结构；即便如此，作者的简短定制 skill 虽然得分最高，也远未稳定执行其核心要求。

## 为什么值得看（钩子）

反直觉之处在于：Agent 并非完全不知道测试工具，也能识别风险点，但“知道名词”和“设计出能暴露错误的测试”之间仍隔着一层；更多测试、更多迭代、更多形式化工具甚至可能只是更昂贵的自我确认。

## 关键细节 / 引述

- 主实验让 GPT-5.6 Sol 以 medium 和 xhigh 两种 effort 用 Rust 实现 Zstd，对比 26 种附加提示条件与 4 个测试 skill；图表以每个条件、每个 effort 平均 80 次运行统计通过全部隐藏测试的比例和成本。作者另在 IMAP RFC 上对各条件做了 40 次运行，并称结论没有实质变化。
- 总体没有任何方法“遥遥领先”。默认组高于平均水平；xhigh 下 fuzzing 和属性测试相关条件平均略好于形式化方法，medium 下则更混杂。作者提醒，不应把条件名当作 Agent 真正使用了对应方法的证据。
- TDD 明显改变了行为：Agent 生成的测试数量约为默认组两倍，160 次里有 67 次在实质实现前先写出失败测试，而默认组为 0 次；但正确率反而下降。它们更常用四条完全相同、甚至很简单的 bitstream 测四流 jump table，因而检测不出流顺序颠倒之类的错误。
- 差分测试的 160 次运行中，135 次做了某种可称为差分测试的动作，但没有一次写出两套完整、独立的实现；需要抓错时，Agent 往往把同一逻辑写两遍，于是把同一个错误复制进两边。
- 普通 fuzzing 多数只生成随机字节，反复进入无效输入／拒绝路径。只有 10／160 次生成了结构化随机输入，其中 5 次找到了真实错误；这是少数显示模型“其实会一点，只是默认不会做”的结果。Kani 也仅在 1／160 次中真正抓到并促使 Rust 代码修复一个非平凡错误。
- 作者临时写的短 skill 要求先列出高风险点和可能误解，再设计能区分结果的非对称／边界检查，并在高风险处独立重新推导；它拿到最高分，但 Agent 几乎从未真正做到“新鲜上下文独立推导”。一次运行甚至准确指出 bitstream 反转有风险，却用了回文输入，导致顺序反转后结果不变，仍放过错误实现。
- 现成 skill 的主要效果常是增加无效劳动。Hegel skill 在 medium 和 xhigh 下成本分别高出 26％和 41％；其正文约 3.4 万字符，还会加载约 4.5 万字符的 Rust 参考，总计超过 2 万 token，并被多次重读，却没有带来正确率提升。
- 单独要求“实现后审计”时，152／160 次确实执行了审计，151 次声称找到问题并据此修改；但平均正确率大致只与默认组相当，而且成本更高。作者的实际经验是，人看过 Agent 的行为后再补几句针对性指令，通常比预先只给一个泛化方法名更有效。

## 与近期的关系

与 09-05 的 DRACO、VeriPhy 不重复：那两条聚焦具体验证／修复系统，本篇比较的是通用编码 Agent 在只得到测试方法名、库名或 skill 时，能否真正把方法用于风险面。与 09-06／09-07 的 Agent 安全事故和模型保护同伴也不是一类话题；这里是软件正确性与测试能力评测，不应泛化成安全事故。可承接近期 Agent 工程化讨论，但新角度是“工具可用不等于方法会用”，重复风险低。
