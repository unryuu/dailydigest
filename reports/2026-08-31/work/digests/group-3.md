# ChatGPT Work 的云端与本地能力边界

- 推荐强度: 强
- 档位线索: 够银牌。它不是一次新功能发布，而是独立实测后把一个命名混乱的产品拆成两套运行形态，并给出云端版相对普通 Chat 的真实能力边界；适合写成产品解剖，不能扩写成 OpenAI 的正式承诺。
- 涉及文章: [Understanding ChatGPT Work](https://simonwillison.net/2026/Aug/30/understanding-chatgpt-work) · Simon Willison’s Weblog · 2026-08-30

## 核心主张

Simon Willison 认为，ChatGPT Work 实际上是两套产品：Work Cloud 运行在云端，可从网页、移动端及桌面端进入；Work Local 则通过桌面应用直接访问本机文件并运行本机程序，更像是为非开发者重新包装的 Codex。作者后续实测集中在 Work Cloud，发现它与普通 Chat 的关键差异不在于“适合完成任务”这类用途描述，而在于联网代码执行、完整浏览器、跨会话持久文件系统、Sites、子 Agent 和自动化等具体能力。

## 为什么值得看（钩子）

OpenAI 用同一个名字覆盖本地和云端两种运行方式，又主要按“用来做什么”而不是“实际上能做什么”解释产品。作者通过实际操作补出了边界，也暴露出一个更重要的问题：云端 Work 同时接触私人数据、不可信网页和外部通信渠道，正好凑齐他所说的提示注入“致命三要素”。

## 关键细节 / 引述

- 两种 Work 当时都只面向每月 20 美元及以上的订阅者；免费用户和每月 8 美元的 Go 用户不能使用。作者还观察到，Work 会话似乎消耗 Codex 配额，而普通 Chat 使用另一套独立配额，但他明确将其表述为自己的理解。
- Work Cloud 的代码执行环境可以访问互联网。作者实测可让它克隆 GitHub 仓库、安装依赖并继续与网页或 API 交互；允许域名可配置，但他观察到默认状态似乎相当开放。
- Work Cloud 能启动完整的无头 Chrome，加载网页、填写表单、截图，并通过 JavaScript 操作 DOM。需要登录时，浏览器会把控制权交给用户输入密码和双重验证码，凭证不必经过模型。
- 每个 Work 会话有独立的 `/workspace/scratch/...` 目录，但这些目录会跨会话保留；作者当时已有 171 个目录。他观察到正在运行的 Work 会话似乎挂载同一个 `/workspace` 卷，一处改动可被另一处立即看到，但它们不共享进程空间，一个会话的 localhost 服务不能被另一个会话访问。
- 普通 Chat 不能启动子 Agent，而 Work 可以让 Sol、Luna、Terra 并行处理复杂项目。作者还让一个新会话列举自身工具，得到 223 个注册工具，其中 6 个来自他自己的 MCP；随后又发现 44 个 Skills，浏览器自动化实际通过 skill 和 `agent.browsers.*` API 暴露。
- 定时提示可以按频率运行，并根据结果决定是否通知用户；作者后来补充，普通 Chat 似乎也能使用这一能力。Work 的差异在于自动化可以结合专属能力，例如定时更新一个 ChatGPT Site，因此不宜把“支持定时任务”单独写成 Work 独占功能。

## 与近期的关系

ChatGPT Work 已于 7 月 9 日公布，这篇不是新的官方公告，而是产品快速迭代后的一次独立拆解。若近期已经报道过 Work 上线或 Codex 改名，存在主题重复风险；本篇的新价值是区分 Cloud 与 Local，并以作者实际观察限定持久文件、浏览器、子 Agent 和自动化的边界，写作时应避开“OpenAI 正式宣布这些能力均有稳定保证”的口吻。
